# Phase 5 Investigation & Evidence Intelligence

Phase 5 adds a dedicated investigation context and evidence-intelligence engine on top of the Phase 4 central orchestrator. Investigation is an evidence workflow, not an action workflow:

```text
INCIDENT → OBSERVE → COLLECT EVIDENCE → NORMALIZE → CORRELATE
  → GENERATE HYPOTHESES → TEST HYPOTHESES → SCORE CONFIDENCE
  → ROOT-CAUSE CANDIDATES → RECOMMEND NEXT STEP
  → HAND OFF TO ORCHESTRATOR
```

The implementation is in `backend/app/investigation/`. It reuses the existing Phase 4 `ToolRuntime`, `ToolRegistry`, `ToolPolicy`, `AIService`, repository, and orchestrator. It does not introduce a second AI provider, tool registry, executor, or approval path.

## Investigation context

`InvestigationContext` is a secret-free, request-safe record containing:

- the incident and investigation identifiers;
- source classification (`LIVE INCIDENT RECORD` or `SIMULATED / CONTROLLED DEMONSTRATION`);
- server-owned lifecycle status;
- normalized evidence and provenance;
- deterministic correlations and their dimensions;
- hypotheses, citations, contradictions, missing evidence, lifecycle status, and next validation step;
- deterministic confidence, component factors, and concise explanation;
- root-cause candidates, evidence gaps, and recommended next step;
- a bounded AI status/summary, if Nemotron was available;
- an auditable timeline and orchestrator handoff status.

The server owns all status transitions. Valid hypothesis statuses are `PROPOSED`, `TESTING`, `SUPPORTED`, `REJECTED`, and `INCONCLUSIVE`. A correlation is always presented as a relationship and never as proof of causation.

Investigation records use an in-memory `InvestigationStore` in this phase. It has incident and request indexes for idempotency, and it deep-copies contexts at the boundary. A future durable adapter can replace the store without changing the HTTP contracts. The existing incident repository also receives normalized evidence, legacy-compatible hypothesis records, and activity events so the established read surfaces retain an auditable view.

## Collection and provenance

Collection is restricted to existing Phase 4 read-only tools:

- `get_logs`
- `get_metrics`
- `get_recent_deployments`
- `inspect_configuration`
- `search_documentation`
- `run_health_check`
- `run_test` (bounded, non-mutating simulator probe)

Every request, execution result, normalization step, failure, and analysis transition emits a timeline/activity event. Tool names are validated server-side before execution. Tool arguments are generated by the server; model output is never executed.

Each normalized `EvidenceRecord` stores the stable evidence identifier, source, type, timestamp, concise summary, collection status, collector, relevance, confidence, bounded raw reference, bounded metadata, and simulator flag. Simulator records have both `simulated: true` and a visible source prefix:

```text
SIMULATED / CONTROLLED DEMONSTRATION · ShopFlow / Payment Service
```

The normalizer treats tool results, logs, documentation, and simulator fields as untrusted data. It keeps identifiers and bounded strings only; it never executes, deserializes, or exposes raw payloads.

## Deterministic analysis

`EvidenceCorrelator` applies bounded rules for temporal proximity, service relationships, deployment proximity, configuration relationships, error/metric alignment, transaction impact, and shared error signatures. Correlation records include the evidence IDs, relationship, reason, dimensions, strength, and temporal delta. They do not assert causation.

`HypothesisEngine` creates candidates only when evidence exists. The five controlled ShopFlow scenario IDs map to deterministic candidate families:

| Scenario | Candidate family |
| --- | --- |
| `payment-failure` | Payment service failure |
| `database-failure` | Primary database connectivity failure |
| `latency-spike` | Downstream dependency latency |
| `bad-deployment` | Recent deployment regression |
| `configuration-mismatch` | Configuration mismatch |

Unknown or live scenarios use incident/evidence signals for bounded fallback inference. Candidate titles are deduplicated within a run. Missing evidence and contradictions remain visible rather than being silently resolved.

`HypothesisScorer` calculates confidence only from server evidence: supporting signal coverage, independent evidence-type coverage, correlation strength, evidence quality, temporal alignment, contradiction penalty, and missing-evidence penalty. It records each factor and a concise explanation. AI confidence, AI status, and AI causal claims are not authoritative.

The server validates all AI hypothesis citations against the collected evidence IDs and resets AI lifecycle/confidence claims before scoring. Nemotron may add an assistive candidate or summary, but it cannot add evidence, choose an authoritative confidence, execute tools, approve remediation, mutate state, or mark an incident resolved. If AI is missing, malformed, unavailable, or invalid, deterministic analysis remains usable where possible and the context records a safe status/error.

## Safe completion and handoff

A supported candidate can produce `COMPLETED` with a `READY` handoff and a recommendation to send the evidence-grounded context to Phase 4. The handoff calls the existing `AgentOrchestrator.start()` boundary. It does not call an action tool directly.

The default test/local orchestrator may be unconfigured. In that case the investigation remains complete, the handoff is `REQUIRES_HUMAN`, and the incident is not resolved. Phase 4 still owns routing, risk, approval, controlled execution, verification, and resolution. An investigation cannot directly execute medium/high-risk actions. No path marks an incident `RESOLVED` without Phase 4 successful verification.

Missing evidence, unavailable tools, malformed AI, conflicting signals, low confidence, cancellation, and failed verification escalate to `REQUIRES_HUMAN`, `INCONCLUSIVE`, `FAILED`, or `CANCELLED` as appropriate. A completed investigation is not downgraded by a later cancellation request.

## API

All routes are under `/api/investigations`.

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/investigations` | List investigation summaries |
| `POST` | `/api/investigations/incidents/{incident_id}/start` | Start or return an idempotent investigation |
| `GET` | `/api/investigations/incidents/{incident_id}` | Retrieve the investigation for an incident |
| `GET` | `/api/investigations/{investigation_id}` | Retrieve the full context |
| `GET` | `/api/investigations/{investigation_id}/summary` | Retrieve a compact summary |
| `GET` | `/api/investigations/{investigation_id}/evidence` | List normalized evidence and provenance |
| `GET` | `/api/investigations/{investigation_id}/correlations` | List explainable relationships |
| `GET` | `/api/investigations/{investigation_id}/hypotheses` | List server-scored hypotheses |
| `GET` | `/api/investigations/{investigation_id}/timeline` | List the audit timeline |
| `POST` | `/api/investigations/{investigation_id}/collect` | Collect additional allow-listed read-only evidence |
| `POST` | `/api/investigations/{investigation_id}/test-hypothesis` | Test one candidate with bounded probes |
| `POST` | `/api/investigations/{investigation_id}/handoff` | Send the context to Phase 4 orchestration |
| `POST` | `/api/investigations/{investigation_id}/cancel` | Cancel without executing an action |

`start` accepts `scenario_id`, `request_id`, and `auto_handoff`. A request ID and incident ID are both idempotent. For a ShopFlow run, use `auto_handoff: false` during a controlled demonstration when the investigation result itself is being inspected.

## Frontend surfaces

`/investigation/{incident_id}` displays start/intake, lifecycle, source classification, provenance evidence, confidence factors, correlations, hypotheses, contradiction/gap signals, root-cause candidates, next step, timeline, and the guarded orchestrator handoff. `/evidence` combines legacy repository evidence with simulator records and labels source/provenance. The UI renders only concise structured summaries; it does not show prompts, completions, raw logs, credentials, or private chain-of-thought.

## Verification

The Phase 5 checks cover:

- all five deterministic ShopFlow scenarios;
- simulator labeling and raw-reference provenance;
- correlation dimensions and non-causation wording;
- deterministic scoring factors and lifecycle status;
- duplicate candidate suppression;
- request/incident idempotency;
- unsafe tool rejection without action execution;
- missing live evidence escalation;
- bounded hypothesis testing and cancellation behavior;
- AI citation filtering and server-owned confidence;
- frontend route/component coverage, typecheck, build, and test execution.
